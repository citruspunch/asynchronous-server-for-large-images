## Context

- Parent goal: UltraTile UTP/1.0 system — Java 21 tiling server + offline viewer + protocol doc
- Requirements for this phase:

FROZEN epoch cleanup on EVERY `newViewEpoch()` (pan/zoom/resize/switch — v1.8 cleared fully only on picker change): in this order — bump epoch FIRST, cancel old awaiters, remove old-epoch `pending` entries, clear old epoch's `retryNeeded` + `terminalFailed`, purge queued (not in-flight) decode payloads of older epochs, move old `BatchState`s to the retained-canceled window (a tile that terminal-failed in E is requestable again in E+1; no canceled-generation pending entry survives to suppress a fresh intent). NO network batch without real headroom: `headroomOk = inflight<MAX_DECODE && queueJobs<DQ_JOBS && freeBytes>=MAX_TILE_BYTES`; batch budget `min(BATCH_CAP, freeJobSlots, max(1,floor(freeBytes/avgTileBytes)))`, `avgTileBytes` = running mean of received TILE lens (seed 131072); END ≠ decoder-ready. Suppression set = cached ∪ pending ∪ decode-queued ∪ decode-IN-FLIGHT (`decodePipeline.has(key)`) ∪ `terminalFailed`(epoch); every TILE checked for `expectedKeys` membership + image/zoom match; per-gen dynamically-budgeted sequential batches; network vs coverage split; switch keeps `nextReqId`, closes bitmaps, discards pre-decode buffers. FROZEN initial camera (removes "reset cam" ambiguity): `camX=W/2, camY=H/2, s=clamp(min(Vw/W,Vh/H),SCALE_MIN,SCALE_MAX)` (no margin fudge — deterministic tests). Duplicated Java constants EXPLICIT (`TILE=512`, `MAX_CACHE=40`, `MAX_TILE_BYTES=2097152`, `BATCH_CAP=30`) — parity with `Config.java` pinned by `scripts/check_const_parity.py`.

## Notes for Implementer

- `classify(reqId)` is THE v1.7 client bridge; v1.8 added the ownership machine; v1.9 adds the epoch boundary: `newViewEpoch()`'s frozen cleanup order is load-bearing (without wholesale old-epoch clearing, a terminal failure or a stale pending entry leaks across intents and either suppresses fresh requests or resurrects dead ones). Both directions have dedicated tests (E→E+1 requestable; rapid double-bump purges).
- Headroom discipline unchanged from v1.8: `headroomOk()` gates SENDING; `batchBudget()` sizes WHAT to send.
- Duplicated constants are a deliberate, pinned trade-off (no build step, no shared module between Java and static JS): the parity script — not discipline — keeps them honest. Any value change MUST update `Config.java` + `viewer.js` + the parity map together.
- Validation builds its own JAR first (`./build.sh`) — fully self-contained like phases 04/05/07.
